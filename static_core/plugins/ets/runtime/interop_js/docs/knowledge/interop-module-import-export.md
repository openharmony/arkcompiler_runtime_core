# Interop Module Import and Export Knowledge

This document records the specification rules for cross-context module import and export between ArkTS-Sta (static) and ArkTS-Dyn (dynamic).

## Core Principle

Use native syntax as much as possible — developers should write cross-context code as if using local-context objects. Import/export follows standard module resolution with virtual module prefixes.

## Physical Constraints

- All cross-context imports must be within the **same application package**.
- Same package must **not** contain files with the same name but different modes (e.g., `index.ts` and `index.ets` exporting under the same alias in the same directory).

## Supported Export Types

- Default exports
- Named exports
- Module namespace exports

## ArkTS-Dyn Importing ArkTS-Sta

```typescript
import { staObject1 } from "../staModule1";        // relative path
import { staObject2 } from "staHar/src/main/ets/pages/staModule3"; // module path
let ns = STValue.findNamespace('staHar.src.main.ets.page.staModule3.staNamespace'); // via STValue
```

**Supported scenarios:**
- Importing classes, interfaces, functions, constants, and variables defined in ArkTS-Sta
- Accessing static methods via static-type proxy

**Unsupported scenarios:**
- Runtime modification of imported object properties, method structure, or prototype chain
- Cross-context inheritance — Dyn context cannot extend imported Sta classes or implement Sta interfaces

**Requirements:**
- Module resolution uses static-type file system module resolution
- Import results must bind to specific ArkTS-Sta type proxy
- Corresponding `.d.ts` type information should be provided via Declgen

## ArkTS-Sta Importing ArkTS-Dyn

```typescript
import { dynObject1 } from "../dynModule1";        // relative path
import { dynObject2 } from "dynHar/src/main/ets/pages/dynModule2"; // module path
let module = ESValue.load('dynHar/src/main/ets/pages/dynModule2'); // via ESValue.load
```

**Supported scenarios:**
- Importing classes, interfaces, functions, constants, and variables defined in ArkTS-Dyn
- Default exports, named exports, and module namespace

**Unsupported scenarios:**
- Cross-context inheritance — Sta context cannot extend imported Dyn classes or implement Dyn interfaces
- `initModule()` import method

**Requirements:**
- Corresponding `.d.ts` type information should be provided via Declgen

**Note:** When ArkTS-Sta imports a `let` variable from ArkTS-Dyn, only reading is supported — modification is not allowed.

## Interop Declaration Files and Glue Code

When a compiler only accepts one syntax specification, interop declaration files (`.d.ets`) and glue code (`.ts`) are generated by the Declgen tool to participate in compilation checking.

- Declaration files path: `build/default/intermediates/declgen/default/declgenV1/.../test.d.ets`
- Glue code path: `build/default/intermediates/declgen/default/declgenBridgeCode/.../test.ts`

**Incremental compilation rules:**
1. Source unchanged, interop files unchanged → no regeneration
2. Source unchanged, interop files modified → no regeneration; if both source and interop files changed, backup interop files
3. Source modified, interop files unchanged → automatic regeneration
4. Source modified, interop files modified → automatic regeneration with backup (`${fileName}.backup`)
